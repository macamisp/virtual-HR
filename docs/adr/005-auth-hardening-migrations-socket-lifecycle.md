# ADR 005: Auth Hardening, Prisma Migrate, Socket Lifecycle, Security Baseline

**Status:** Accepted
**Date:** 15 October 2026
**Requirements:** FR-AUTH-002, 003, 004, 008, 010, 011 (SRS 5.1); FR-ATT-004/017; AGENTS.md security rules.
**Supersedes:** the `schema.sql` parts of ADR 002, 003 and 004, and the AUTH ID mapping in ADR 004 (see `docs/traceability/auth.md`).

## 1. Migrations: Prisma Migrate only

- `apps/api/src/attendance/schema.sql` is deleted. The schema lives in `apps/api/prisma/schema.prisma` and versioned SQL in `apps/api/prisma/migrations/`.
- `20261015000000_init`: tables generated by `prisma migrate diff --from-empty`, followed by a hand-written security section carried over from `schema.sql`: `hrvo_app` / `hrvo_retention` roles (NOSUPERUSER NOBYPASSRLS), grants, ENABLE + FORCE RLS with the strict `org_id` policy on every tenant table, append-only REVOKEs on `audit_logs`, `presence_events`, `monitoring_consents`, and the SECURITY DEFINER lookup functions (now with `REVOKE ALL FROM PUBLIC`).
- `20261015000100_auth_hardening`: `auth_sessions.revoked_reason`, `password_reset_tokens` (+ RLS), status-aware `fn_lookup_session_for_refresh`, `fn_lookup_password_reset`, and the `hrvo_auth_events` NOTIFY triggers.
- `schema.prisma` declares `directUrl = DIRECT_DATABASE_URL`: migrations run as the schema owner, the app connects as `hrvo_app`.
- **Role passwords are not in migration SQL** (no secrets in code). `npm run db:provision-roles` (`prisma/scripts/provision-db-roles.ts`) sets them from `PGPASSWORD` / `PGRETENTION_PASSWORD`. It changes credentials only, never schema.
- Prisma CLI and client are pinned to exactly `6.19.3`. Prisma 7 changes datasource configuration and is a separate decision.
- CI applies migrations to an empty Postgres, provisions roles, fails on drift between migrations and `schema.prisma`, then typechecks and runs all tests with coverage.
- Making the Prisma model the source of truth added a `teams.lead_id → users` FK that `schema.sql` lacked; two test seeds were reordered for it.

**Existing local databases** built from `schema.sql` have no `_prisma_migrations` history. Recreate them (`prisma migrate reset`, destructive) or baseline them (`prisma migrate resolve --applied 20261015000000_init`, then `npm run db:migrate`).

## 2. Socket lifecycle (FR-AUTH-003)

- Access tokens now carry `sid` (auth session id), `iss=hrvo-api`, `aud=hrvo-api`.
- Handshake auth runs as Socket.IO middleware (`afterInit`), so no handler ever sees an unauthenticated socket. The session must not be revoked (rotation excepted) and the user must be `ACTIVE`.
- **Expiry:** each socket has a timer at the token's `exp`; on expiry it emits `auth:expired` and is disconnected. A client extends the socket by sending `auth:refresh { token }` with a newer access token for the same user/org.
- **Revocation:** `auth_sessions.revoked_reason` distinguishes `ROTATED` (normal refresh) from `LOGOUT`, `FAMILY_REUSE`, `PASSWORD_RESET`, `USER_DEACTIVATED`. Triggers publish `session_revoked` (non-rotation revocations, deletions) and `user_deactivated` (status leaves `ACTIVE`) on channel `hrvo_auth_events`. Each API instance holds a dedicated `LISTEN` connection; sockets join `family:<id>` and `user:<id>` rooms and are disconnected with `auth:revoked { reason }`. Payloads contain IDs only.
- **Safety net:** every `SOCKET_REVALIDATE_MS` (default 60 s), and after the listener reconnects, all sockets are re-validated against the database.
- Logout now revokes the caller's own session family, taken from the verified token. The previous version revoked any `sessionId` in the request body within the org.
- Suspended/offboarded users can no longer log in or refresh.
- Cookie-borne access tokens are no longer accepted (HTTP or WebSocket), so there is no ambient credential for CSRF / cross-site WebSocket hijacking.

## 3. Mandatory 2FA enrollment (FR-AUTH-004)

- SUPER_ADMIN, ADMIN, HR_MANAGER, HR without TOTP receive only a 10-minute **enrollment token** (`aud=hrvo-mfa-enroll`, no `sid`). It is accepted solely by `POST /auth/2fa/setup` and `POST /auth/2fa/verify` (`@AllowMfaEnrollment`). A successful verify enables 2FA and issues the full session.
- `setup` is refused once 2FA is enabled, so a stolen access token cannot replace the authenticator.
- Fixed: `setup2fa`, `verifyAndEnable2fa` and recovery-code consumption ran outside tenant context, so under FORCE RLS their writes silently affected 0 rows (enrollment never worked; recovery codes were never consumed). Recovery codes were also unusable because the login DTO only accepted 6-character codes.
- Failed TOTP/recovery attempts count toward the FR-AUTH-007 lockout.
- Trade-off: first enrollment is trust-on-first-use. Whoever holds the password at first login enrolls the authenticator. Mitigated by invitation-only accounts and audit entries.

## 4. Password reset (FR-AUTH-008)

- `POST /auth/password/forgot` always answers 202 with the same body. For each ACTIVE account with that email, it invalidates older links, stores `sha256(token)` with a 30-minute expiry, audits, and mails `APP_WEB_URL/reset-password#token=…` (fragment, so the token is not sent to servers or in Referer).
- `POST /auth/password/reset` validates the new password first (so a rejected password does not burn the link). It then atomically claims the token (`used_at IS NULL AND expires_at > now`), sets the Argon2id hash, clears lockout, revokes all sessions (reason `PASSWORD_RESET`, which disconnects sockets) and audits.
- Mail: `MAIL_TRANSPORT=smtp` is a minimal plaintext SMTP client for Mailhog and is refused in production; `memory` is for tests. A production provider is still open.

## 5. Security baseline

- `helmet` 8.3.0 (approved): CSP `default-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, nosniff, CORP same-site, HSTS in production.
- CORS: exact-match allow-list from `CORS_ORIGINS` (required in production, `*` rejected), shared with the Socket.IO adapter. WebSocket handshakes with a disallowed `Origin` are refused (`allowRequest`), because CORS does not cover the websocket transport.
- Rate limits with `@nestjs/throttler` 6.7.1 (approved): named buckets `login`, `refresh`, `passwordReset` per client IP (`2fa/verify` uses `login`), and a `heartbeat` bucket per user via the throttler storage. Limits come from env. **The store is in-memory, so limits are per instance**; a Redis store is required before horizontal scaling.
- CSRF for cookie-based `/auth/refresh`: cookie `SameSite=Strict`, `HttpOnly`, `Path=/auth/refresh`, `Secure` in production; plus required header `X-HRVO-CSRF: 1` (forces a preflight the allow-list rejects) and an allowed `Origin` when present. A refresh token sent in the body is not ambient and needs neither. *(Superseded 15 Oct 2026, ADR 006 §8: body tokens are no longer accepted or returned; every refresh is cookie-only and CSRF-checked.)*
- Production refuses to start with a missing/placeholder `JWT_SECRET`, missing `CORS_ORIGINS`, the local breach stub, or the dev SMTP transport.
- Removed logging of token prefixes (JWT guard), and test/demo output of invite tokens, access tokens and heartbeat secrets.

## 6. Breached-password check (FR-AUTH-002)

`HibpRangeChecker` calls `https://api.pwnedpasswords.com/range/{first 5 hex of SHA-1}` with `Add-Padding: true` and ignores count-0 padding rows. Only the prefix leaves the server. It fails closed: if the API is unreachable, the password is not accepted (HTTP 503). `BREACHED_PASSWORD_CHECK=local` selects an offline blocklist stub for tests and CI only.

## 7. Browser heartbeat signer (FR-ATT-004)

`packages/shared/src/attendance/heartbeat-signer.ts` holds the single canonical-string definition, used by both the Node validator and a WebCrypto (`crypto.subtle`) HMAC-SHA256 signer for browsers. Key = UTF-8 bytes of the session secret, matching `createHmac('sha256', secret)`.
