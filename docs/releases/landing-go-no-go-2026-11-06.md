## 5. Current root-domain behaviour (public, read-only checks)

- DNS: zone on Cloudflare (`shubhi` / `logan.ns.cloudflare.com`). `virtual-hr.site` has proxied
  A/AAAA records (Cloudflare anycast IPs); `app.` and `api.` the same. **`www.virtual-hr.site` has
  no record.**
- HTTP: `https://virtual-hr.site/<any path>` and `http://` → **301 `https://app.virtual-hr.site/`**
  generated at the Cloudflare edge (`server: cloudflare`, no origin headers, path dropped, no
  `Cache-Control`). This is a Cloudflare Redirect Rule, Page Rule or Bulk Redirect, and it must be
  replaced.
- Not visible from outside (to confirm in the dashboard or on the host before the change): which rule
  type it is, what the proxied apex record points to (a placeholder IP or an existing tunnel
  CNAME), and whether the tunnel is managed in the dashboard or from `config.yml` on the host
  (systemd `hrvo-cloudflared`).

## 6. Cloudflare deployment plan (needs approval; operator steps)

**A. Before.** Record the current state: screenshot or export the redirect rule; the apex DNS
record (type, target, proxied); the tunnel's public hostnames or ingress; the host checkout
(`44ea7f3`) and live web image ID. Tag the live web image for rollback: the compose file runs it as `hrvo-web:https-20261101T083259Z-695e08`; add the tag `hrvo-web:v3-44ea7f3` to the same image ID before building.

**B. Web image (production host, runbook §5, web only).** Check out `a9b6714` (or the merge
commit of PR #7 once merged: same tree), rebuild **web only**, `up -d --no-deps web`. No
migration; API, Postgres, Redis, storage untouched. Check: `https://app.virtual-hr.site/` → login,
sign-in works, office loads; `https://app.virtual-hr.site/welcome` renders; on the host
`curl -sI -H 'Host: virtual-hr.site' http://127.0.0.1:<web port>/` → 200.

**C. Tunnel hostname.** In the same tunnel, add `virtual-hr.site` → the same service as
`app.virtual-hr.site` (the web container). Do not set an `httpHostHeader` override: the middleware
needs the original Host. Dashboard-managed tunnel: Public Hostname → the apex DNS record becomes a
tunnel CNAME. `config.yml` tunnel: add the ingress rule above the catch-all, `cloudflared tunnel
route dns <tunnel> virtual-hr.site`, restart `hrvo-cloudflared`.

**D. Remove the old redirect.** Disable (do not delete) the edge rule that 301s
`virtual-hr.site/*`. Order: C then D directly after, so the gap is seconds.

**E. www (optional).** Add `www.virtual-hr.site` to the tunnel too; the app answers 308 to the apex.
Without it, `www` keeps not resolving, as today.

**F. Verify live.** `curl -sI https://virtual-hr.site/` → 200, no `location`; `/login` → 308
`https://app.virtual-hr.site/login`; `robots.txt`, `sitemap.xml`; page source has the canonical
link and `og:*` tags; Log in and Get started in a browser; phone width; app regression (login with 2FA,
office, attendance badge). Purge the Cloudflare cache for `virtual-hr.site/*` if the old 301 is
still served.

**Known limit:** browsers that already followed the old 301 may keep sending `virtual-hr.site` to
the app from their own cache (a 301 without `Cache-Control` can be cached indefinitely). New
visitors and search engines see the page; affected browsers recover when their cache is cleared.
This cannot be fixed from the server.

## 7. Rollback

- **Root domain only (seconds, app unaffected):** remove the `virtual-hr.site` (and `www`) tunnel
  hostname, restore the apex DNS record recorded in A, re-enable the disabled redirect rule.
  Check: `curl -sI https://virtual-hr.site/` → 301 `https://app.virtual-hr.site/`.
- **Web image:** retag `hrvo-web:v3-44ea7f3` → `hrvo-web:https-20261101T083259Z-695e08`, `git checkout --detach 44ea7f3`,
  `up -d --no-deps web`. No database restore: this change has no migration and stores nothing.
- Triggers: app login/office regression, landing page error, CTAs not reaching the app, an
  unexpected redirect loop.

## 8. Recommendation

**GO** for deploying `a9b6714` (or the PR #7 merge commit, same tree) to the root domain,
**subject to your deployment approval** and these conditions:

1. Step A done first: the existing edge redirect rule, apex DNS record and tunnel mode are recorded,
